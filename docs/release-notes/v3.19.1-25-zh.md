# CCSwitchMulti v3.19.1-25

这是针对 `v3.19.1-24` 的 Codex Windows 启动热修复。它解决了部分用户进入 “Finish Windows setup” 后点击重试仍不弹 UAC、无法完成 Windows setup 的问题。

## 修复内容

### 1. 修复 Codex 模型目录缺失必填字段

- `v3.19.1-24` 为避免未知第三方模型错误继承 GPT 推理档位，会清除该模型的 reasoning 字段。
- Codex 的 `ModelInfo` 允许省略默认推理强度，但要求每个模型都必须包含 `supported_reasoning_levels`；即使模型没有可选强度，也必须写成空数组 `[]`。
- 本版本对未知模型和只有 thinking 开关的模型保留空数组，对 DeepSeek、GLM、Grok、Step 等已声明能力的模型继续写入各自真实档位。

### 2. 恢复 Windows setup 与 UAC 调起链路

- 原故障并不是 Windows UAC、Codex sandbox helper 或 MSIX 权限损坏。
- 损坏的 `cc-switch-model-catalog.json` 会让 Codex 在读取配置时失败；`windowsSandbox/setupStart` 因此在启动 helper 之前就返回 `invalid_config`，表现为点击重试没有 UAC。
- 模型目录恢复为 Codex 可解析结构后，`config/read` 与 `windowsSandbox/readiness` 可正常完成，Windows setup 不再被 CCSwitchMulti 配置阻断。

## 受影响范围

- 已安装 `v3.19.1-24`，并在 MultiRouter 中包含 Qwen、Kimi、MiniMax、MiMo、SiliconFlow、旧配置迁移模型或未声明 reasoning 的自定义模型时，可能触发该问题。
- 只要目录中有一个模型缺失必填字段，Codex 就可能拒绝读取整份模型目录，因此影响不限于那个模型本身。
- `v3.19.1-23` 不会生成该缺失字段结构；从 `v3.19.1-24` 降回 `v3.19.1-23` 后恢复，是该问题的有效现场特征。

## 升级方式

1. 安装 `v3.19.1-25`；无需删除 CCSwitchMulti 数据库、`~/.codex`、sandbox 用户或防火墙规则。
2. 启动 CCSwitchMulti，重新保存或启用一次当前 MultiRouter 方案，使 `cc-switch-model-catalog.json` 重新生成。
3. 完整退出并重启 Codex/ChatGPT app-server，再新建会话。
4. 如果此前停留在 “Finish Windows setup”，重新点击一次 Windows setup；此时配置读取不应再阻断 helper/UAC。

## 验证

- 回归测试覆盖：未知第三方模型不继承 GPT 档位，同时保留必填空数组。
- 目录聚焦测试覆盖已声明 reasoning、空 effort、未知模型、模型菜单和 MultiRouter 投影。
- 完整 Rust、前端、类型、格式、构建及真实 Codex 配置读取结果以本 tag 的最终发布验证为准。

## 已知边界

- 如果升级后 UAC 能弹出但 setup 仍失败，应继续检查本机管理员策略、用户/组创建、防火墙规则和 sandbox 用户登录权限；这与本次“配置读取阶段阻断 helper”不是同一个故障。
- 正式 Release 成功不代表用户机器已经自动安装本版本；升级后仍需让 CCSwitchMulti 重新生成目录，并完整重启 Codex app-server。
