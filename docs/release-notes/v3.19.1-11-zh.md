# CCSwitchMulti v3.19.1-11

本版本修复官方 DeepSeek 在 Codex MultiRouter 中选择 Chat 后无法稳定继续工具循环的问题。根因不是 DeepSeek Chat 不支持工具调用，而是 CCSwitchMulti 的启动期数据修复会被同一 Router 内的 Flash 路由干扰，把独立的 Pro/Chat 路由反复改写成 Flash/Responses，造成 UI 选择与实际出站协议不一致。

## 修复内容

- DeepSeek 路由迁移现在按每条 route 的 `targetProviderId` 读取目标 Provider 的真实模型目录，不再从整份 MultiRouter JSON 猜测协议归属。
- 只包含 `deepseek-v4-pro` 的官方 DeepSeek Provider 会稳定保持 `openai_chat`，Codex 对外仍使用 Responses，由 CCSwitchMulti 在内部转换到 `/chat/completions`。
- 只包含 `deepseek-v4-flash` 的 Provider 继续使用官方原生 Responses，不改变现有 Flash 路由能力。
- 兼容旧版把 Flash 与 Pro 放在同一 Provider 的配置，继续拆分成原生 Responses 与 Chat 两条路由。
- 已被旧迁移污染的 Pro route 会在启动时自愈：恢复 `deepseek-v4-pro` 的模型匹配、前缀、模型映射和 Chat 协议。
- 修复幂等性缺口：重复启动不再改变已修复的路由内容。

## 验证

- RED 回归在旧逻辑上稳定复现独立 Pro/Chat route 被改写成 Flash/Responses。
- 修复后 DeepSeek 启动迁移测试 `2 passed, 0 failed`，并验证第二次迁移内容完全不变。
- DeepSeek 官方 Chat Completions 工具调用实测返回流式 `tool_calls` 与 `finish_reason=tool_calls`，证明 Chat 路径具备 Codex 工具循环所需的上游语义。
- 完整源码、构建、数据库副本迁移和安装后运行时验证结果以最终构建记录为准。

## 升级方式

关闭 CCSwitchMulti 后覆盖安装本版本，再重新启动 CCSwitchMulti 与 Codex。应用启动时会自动修复受影响的 DeepSeek Pro/Chat 路由；不会删除 Provider、API 配置或历史会话。

对于大对话，不建议把 Pro/Chat route 强制改成 DeepSeek 原生 Responses 来规避问题：Codex 仍应连接 CCSwitchMulti 的 Responses 门面，由 CCSwitchMulti 在内部使用官方 Chat Completions 完成协议转换与工具循环。
