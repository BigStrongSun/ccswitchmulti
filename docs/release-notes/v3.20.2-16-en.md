# CCSwitchMulti v3.20.2-16

Fixes a defect where one network hiccup could take the OpenAI Official route completely offline for half an hour.

## Problem

Starting at 2026-09-15 09:17:59, TLS handshakes to chatgpt.com failed repeatedly (`unexpected EOF during handshake`). For the next ~30 minutes every Codex request returned `503 无可用 Provider` **within 3 ms**, with no upstream request recorded at all — the request was never sent.

Root cause: account-pool soft-avoid was treated as a hard failure.

- Transient network failures were counted as **per-account** consecutive failures. The two accounts reached 9 and 6 consecutive failures by 09:18:35 and 09:19:12 and each escalated up the soft-avoid ladder (30s → 120s → 600s → **1800s**) to a **30-minute** avoidance.
- With every pool account avoided, `ordered_pool_entries` returned empty, the pool expansion produced zero candidates, and the router returned `503 无可用 Provider` **without ever contacting upstream**.
- Because nothing was ever attempted, no success could clear the soft-avoid, so even after the network recovered the outage lasted the full 30 minutes. The error text never mentioned the account pool either.

## Fix

- **Soft-avoid is now a preference**: when every pool account is soft-avoided or cooling down, the pool falls back in "earliest recovery" order so the request actually reaches upstream and returns a real result. Accounts that genuinely cannot be used (needs re-login, unusable credential, quota below reserve) are still excluded — fail-closed is preserved.
- **Real diagnostics**: the fallback logs the earliest recovery time and candidate count, and an empty account pool logs `[CodexOAuthPool] [POOL-001]` instead of a 503 with nothing in the log.
- **Honest error text**: the `503` cause is now `无可用 Provider（没有可尝试的上游候选：账号池全部不可用或全部被熔断拒绝）`.

## Verification

- New regression `all_soft_avoided_accounts_still_probe_earliest_recovery`: after all three accounts (including native) accumulate three transient failures each, the pool must still return every candidate (the old code returned none).
- `cargo test --lib proxy::` 1968 passed / 0 failed; `cargo fmt` clean.
- Field evidence: 240 consecutive requests to the official route from 09:19:13 were 100% 3–6 ms `503`s in `proxy_request_logs`, and `codex-router.log` shows the last real upstream attempt at 09:19:12 — exactly when both accounts hit their 30-minute soft-avoid.
