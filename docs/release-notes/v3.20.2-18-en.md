# CCSwitchMulti v3.20.2-18

Three fixes: notification layer not clickable while a modal dialog is open (the prepared v3.20.2-17 content), the refresh flow failing at the final "verify runtime" step after a 450-second stall, and a confirmation page that did not state whether anything was actually wrong. v3.20.2-17 was never published separately; its content is included here.

## 1. Notification layer not clickable under modal dialogs

Radix modal dialogs set an inline `pointer-events: none` on `document.body` (marking only the dialog content as `auto`). The sonner notification layer is mounted inside `#root`, and `pointer-events` is inherited, so the whole notification layer — including its “View logs” button — became non-interactive.

**Fix**: the notification container declares `pointer-events: auto`; sonner's own `[data-sonner-toast][data-visible='false'] { pointer-events: none }` still applies.

## 2. “Verify the new runtime” stalled for 450 seconds and then reported `codex_paginated_history_projection_not_caught_up`

- The repair phase itself succeeded (the recovery snapshot shows all 1114 cursors updated; a read-only re-check confirms all 1114 are at/after their repaired offsets).
- The old check required **every** repaired cursor to advance to the file length captured at repair time. Codex Desktop materializes history lazily (only when a task is opened or continued), so most threads are never touched and the condition is unreachable — the flow waited the full 450 seconds and failed even though the repair had already taken effect.
- **Fix**: the criterion is now "is the cursor still inside a record?"
  - `damaged`: the cursor points inside a record (the real damage) → still fail-closed.
  - `pending`: the cursor sits on a valid record boundary and Codex simply has not materialized to EOF yet → treated as healthy, no longer blocking, with one log line reporting how many are pending.
- The follow-up rewrite (aligning a cursor stuck on verified duplicate metadata back to the file's actual ordinal) now runs **at most once per verification**, instead of repeatedly writing to Codex's projection database while Codex is running.

## 3. The confirmation page did not say what was wrong or what the button would do

The “Confirm Codex state refresh” page now states the situation up front:

- With repairable files: `History needing repair: N file(s) (duplicate ordinals X · migration cursors Y · parent references Z)`.
- Kept-as-is only: `No history files need repair; N file(s) stay unchanged and are never rewritten automatically.`
- Neither: `No history files need repair.`

The confirm button is renamed accordingly — “Reapply configuration and open” when there is nothing to repair. The previous generic paragraph is now a “Repair scope and boundaries” section that keeps all the detail.

## Verification

- New Rust regressions: `repaired_cursor_on_a_record_boundary_counts_as_caught_up_pending_lazy_materialization` and `repaired_cursor_inside_a_record_is_still_damaged`.
- New frontend regressions: `sonner.test.tsx` (toast action stays clickable under a modal lock) plus the confirmation page's no-repair wording and button rename.
- `cargo test --lib paginated_history`, `cargo test --lib proxy::`, `cargo fmt`, `tsc --noEmit`, Prettier are green.
