# CCSwitchMulti v3.20.4-17

## MultiRouter 保存门禁：从“错误码”变成“可操作阻塞”

- 修复 MultiRouter 向导第 12 步“保存并启用”在遇到“已启用、可路由，但模型没有声明推理能力”的 Sub-Agent 角色时，只回显 `unknown_reasoning_capability_requires_declaration` 错误码：既不说明是哪个模型，也不给任何出口，用户只能在 13 步向导里反复点保存。
- 后端保存门禁现在在错误码之后列出全部被阻塞的模型（去重、按名称排序），前端据此展示具体模型、所属模型源和三个可执行出口：
  - “在 `<Provider>` 中声明推理能力”——直接打开对应模型源的配置；
  - “禁用这些 Sub-Agent 角色并保存”——只关闭这些角色的 `enabled`，保留问卷、覆盖和输入模态，随即重试保存；
  - “打开 Sub-Agent V2 工作台”——回原工作台手动处理。
- 向导会记录本轮的禁用集合，后续保存不会把这些角色重新打开；保存成功后提示消失。

## 行为边界未改变

- `unknown` 仍然不能靠 `delegated` 绕过：没有声明推理能力的模型不会静默回落到“交给上游默认”。
- 只有 `enabled` 且实际可路由（会生成角色）的 profile 才会阻塞保存；`disabled` 和不可路由的 profile 不受影响。
- 被禁用只是“本轮不生成该角色”，不是删除配置；声明能力后可在 Sub-Agent V2 工作台重新启用。

## 典型触发场景

先前的向导把某个模型选作 Sub-Agent 候选，之后对应模型源的目录没有声明该模型的推理能力；当 MultiRouter 新增一条指向该 Provider 的 route 后，这个旧的 `enabled` profile 变成可路由，保存随即被门禁拦下。旧版本在这里只给错误码，新版本会点名模型并给出上面三个出口。

## 升级说明

- 无数据库 schema 变更，无新增依赖；安装并重启新版本后修复生效。
- 已经被同类配置卡住的用户：新版本会在保存页指出具体模型，可以直接禁用该角色完成保存，也可以先到模型目录声明推理能力再保存。
