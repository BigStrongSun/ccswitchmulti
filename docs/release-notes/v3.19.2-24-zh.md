# CCSwitchMulti v3.19.2-24

这是 `v3.19.2-16` 以来 Codex 路由与兼容体系的完整累计版本。相对 `v3.19.2-15`，发布候选累计约 180 个提交、249 个文件和 6.5 万行新增，覆盖 Provider 分流、MultiRouter/V2 Sub-Agent 自动同步、双协议深探测、完整设置向导、推理与工具续轮、Codex 配置/历史恢复以及 Windows 安全升级。

## 先说清楚：Provider 分流到底是什么

这套能力不是在 UI 中再增加一层需要用户维护的 `BrokerProvider`。实际架构是：

1. **Provider 保存真实配置与模型能力**：endpoint、认证、协议、模型、上下文、输入模态、推理档位、Ultra、缓存、显示名、启用状态和排序。
2. **MultiRouter 保存路由策略**：目标 Provider、模型选择、别名、认证策略、路由顺序和 V2 Sub-Agent 配置。
3. **编译器生成运行投影**：每次从最新 Provider 快照生成 Codex 模型目录、缓存、受管 Agent TOML 和当前 live 配置；投影损坏可以重建，不反向污染 Provider。

因此用户仍然只看到扁平的普通 Provider 与 MultiRouter 卡片。普通单协议 Provider 标记 `Responses` 或 `Chat`；同一逻辑 Provider 需要两种上游协议时显示“自动适配 · Responses + Chat”；真正的跨 Provider 路由继续显示 `MultiRouter`。

## 1. Provider → MultiRouter 的跨模型自动同步

- `mode=all` 跟随目标 Provider 的全部启用模型。Provider 新增、删除、停用、改名、改协议、改上下文、输入能力或推理档位后，Router、模型目录和已初始化 V2 Sub-Agent 在同一 mutation 链中重新编译。
- `mode=include` 保留用户明确选择的模型白名单。Provider 的能力变化仍同步，但不会擅自把新模型加入路由。
- Provider 的公开模型名、上游模型名与路由别名分离。同名模型按来源形成稳定身份，日志和诊断显示真实 Provider，不再只显示内部 route ID。
- 未选择、未匹配、已停用或身份歧义的模型严格 fail closed，不会回退到默认 Provider 或第一条路由，从根上避免“模型悄悄跑错供应商”。
- 多个 Router 共用模型源时，只有当前活动 Router 能写共享投影；活动归属不明确时拒绝发布，避免相互覆盖。
- Router 数据库只保存策略。模型目录、`models_cache`、配置指针/指纹、受管 Agent TOML、投影状态和查询缓存属于可重建投影；Provider 认证、Common Config 和用户自有 TOML 字段不由 Router 接管。
- Provider 保存与 Router 投影解耦：数据库事务已成功但 live 投影失败时，会报告“已保存、待刷新”并保留可重试诊断，不把已提交数据伪装成保存失败。

## 2. MultiRouter 本身的重做

- schema v2 路由统一以 `targetProviderId + modelSelection + aliases + authPolicy` 表达，不再把 Provider 的 endpoint、协议或模型目录快照复制进每条 route。
- 认证兼容 `source/accountId`、账号池和 Provider 自有认证；清理旧 `authProvider`、`apiFormat`、`match` 等污染字段，避免迁移后持续触发 `invalid_v2_schema`。
- 模型排序、启停、别名、推理配置和路由预览使用同一编译结果。目录刷新不会复活已停用模型，也不会让 UI 与运行路由各持一套状态。
- Add/Edit、MultiRouter 向导和 Universal Provider 统一使用 Protocol Lab 与 Provider Set 的 Preflight → Prepare → Commit 工作流；Single/Split 都由一次原子提交完成。
- 同一 Provider 内全部模型使用同一协议时保存为严格单协议 Provider；模型实际协议混合时保存一个可见逻辑门面和两个隐藏同协议叶子。叶子不出现在普通列表，也不能被直接编辑、切换或删除。
- 自动 Split 不再让普通用户做没有意义的二次确认；高级模式仍允许逐模型选择“跟随自动 / Responses / Chat”，Responses 与 Chat 的探测证据分开保存，用户覆盖不会擦掉另一条协议的结果。

## 3. V2 Sub-Agent、推理强度和模型顺序

- V2 Sub-Agent 直接读取 Router 编译后的 Provider 目录；写入、投影和回读校验使用同一 Provider 上下文，修复保存成功后又提示角色文件不存在的问题。
- 角色名称、描述、开发者指令、昵称候选、推理策略和输入模态区分自动值与手工覆盖；模型不在投影目录、被路由排除或别名不匹配时显示具名诊断，不再留下无法解释的空字段。
- `mode=all` 新增模型会为已初始化的 V2 Agent 创建默认关闭 Profile；模型停用/删除后保留原 Profile 并标记不可路由，避免用户手工配置被静默删除。
- 同名消歧或目录别名变化会同步迁移 Profile key、`model` 和 `spawnAgentModels`。模型确实下架时才保留为可见的 unroutable 状态。
- 推理强度、Sub-Agent 和模型顺序是彼此独立的设置入口，不与协议探测混成一个开关。向导保存成功后提供三个后续入口，也保留历史修复入口。
- 推理档位按 Provider 能力约束；不支持的 `high/xhigh/max/ultra` 会钳制或明确报错，不再让第三方模型错误继承 `reasoning_effort=none` 或发送上游不接受的档位。

## 4. 完整设置向导

- 恢复 13 个常规页面：开始、环境检查、来源就绪、来源选择、目录同步、协议深探测、模型选择、模型顺序、推理、Sub-Agent/工具、路由确认、保存启用、真实请求验收。
- 零 Provider 用户会动态看到第 14 页“接入第一个模型源”；新增完成后按真实 Provider ID 自动选中，不按名称或临时索引猜测。
- 后续页面可以预览，但前置步骤未完成时不可编辑，并明确告诉用户需要先完成哪一步。
- 目录同步与协议深探测拆页。深探测展示 Responses/Chat、SSE 流式、推理语义、强制工具调用和工具结果续轮五个阶段，不再使用旧的“返回一段文字即通过”浅检测。
- 批量进度按 `(Provider, model, protocol)` 聚合；同名模型不会跨来源折叠。后端漏回事件时生成具名阻塞失败，不再出现 Qwen `0/0/0` 却可继续的矛盾状态。
- 向导仍走当前批量原子事务，不恢复旧版逐个保存 Provider、最后单独写 Router 的非原子流程。

## 5. 双协议 Protocol Lab 与第三方模型适配

- 每个启用模型分别验证 Responses 和 Chat Completions；固定协议的官方/OAuth 来源不会重复计费探测。
- 探测与真实代理共用请求 preparer，覆盖 endpoint、认证、公开名到上游名映射、Custom User-Agent、Header/Body override、推理参数、工具 schema 和请求预算。
- 证据按 Provider、模型、协议和完整请求指纹独立保存。endpoint、Key、映射、UA 或 override 变化后旧结果标记 stale，不会被误用。
- HTTP 521/5xx、网络、超时、401/403/429 是可用性或认证错误，不能判成“不支持该协议”；恢复后可以重新探测。
- Responses 必须到达合法终态。只有 `response.created/in_progress` 后提前 EOF、reasoning-only 假完成、不完整工具调用或缺失终态都会变成明确协议错误，不再让 Codex 把未完成任务当成正常结束。
- Responses 工具续轮支持原生 reasoning item、真实 `reasoning_text` content 和 omit 三种回放；只有明确 400/422 replay-shape 拒绝才逐级降级，工具调用与工具结果始终保留。
- 可读 raw reasoning 映射为 `reasoning_text`，只有上游原生 summary 才映射为 `reasoning_summary_text`；不为了 UI 显示伪造摘要。
- Qwen/vLLM、GLM、Kimi、DeepSeek、MiniMax 等来源按当前 endpoint 和实际响应选择协议，不再靠模型名称硬编码。SSE keep-alive 降低长时间推理被网关提前断开的概率。

## 6. v24 新修复的三个公开问题

- **#80 严格 Responses 上游 400**：第三方 reasoning 回放保留真实 `content[].reasoning_text`，同时写入 schema 必填的空 `summary: []`。不再因删除 `input[n].summary` 被 Paratera/OpenResponses 一类严格实现拒绝，也不把 raw reasoning 填进 summary 冒充摘要。
- **#81 旧异常退出告警反复出现**：ActivePreviousInstance、ConfirmedCrash、UncleanExit 等启动分类只在当前启动代际待处理；下一次正常启动后旧分类自动过期。Provider 恢复或端口接管等真实失败仍跨代保留到用户确认，日志历史不删除。
- **#82 关闭接管仍重写模型目录**：启动目录对账先检查 Codex takeover 开关。关闭后即使 live TOML 残留 CCSM 目录指针，也不会刷新或覆盖用户目录；重新启用接管后才恢复正常投影。

## 7. Codex 配置所有权、启动和历史恢复

- 一致性检查只比较 CCSM 拥有的模型、当前 Provider、目录指针和受管路由字段。Codex 自己维护的 `agents.*`、`desktop.*`、`developer_instructions`、MCP command/env、plugins 和 projects trust 保留且不触发漂移。
- 所有写入从最新磁盘快照合并并使用 CAS 重试；不会整份恢复旧备份覆盖 Codex 新字段。托管激活使用独立内容指纹，不再把整个 `config.toml` 的 mtime 当成生效时间。
- “随 CCSwitchMulti 启动 Codex”位于配置、模型目录、15721 接管和复检之后。失败时阻止 Codex 在旧配置上启动；已运行的 Codex 不会被自动关闭。
- “Codex 状态与修复”把配置/app-server 生效、单任务分页历史修复、Renderer 跨 Provider 历史查询拆成三项；Renderer 注入失败只显示可重试警告，不覆盖前两项成功结果。
- Windows 新版 `ChatGPT.exe` 桌面壳与 `codex.exe app-server` 都进入身份快照。刷新只结束逐个复核的 PID，不使用可能递归误杀 CCSM 的 `taskkill /T`。
- 超长单任务的相邻重复 ordinal 修复保留全部 JSONL 记录、先同目录备份再原子替换；非重复回退/断档 fail closed，不重置 SQLite，也不通过修改时间伪造恢复。

## 8. Windows 端口接管与安全升级

- 15721 被旧 CCSM 占用时提供“解除占用并恢复接管”，只接受路径、PID、启动时间和文件身份完全匹配的已验证旧实例；未知程序、PID 复用或二次抢占一律拒绝。
- AppContainer LocalCache 投影使用卷/文件 ID 证明与安装目录是同一程序，不再因路径字符串不同误判为外部占用。
- 安装替换事务覆盖进程复核、端口释放、运行 marker 退役、静止快照、备份、安装、payload hash、单 listener、health 与 takeover 验证；关键步骤失败回滚或 fail closed。
- 启动恢复、配置一致性、异常退出和路由接管弹窗按优先级串行显示，确保当前可见层能够点击。

- #80、#81、#82 已按当前主线架构重新实现并加入 v24，不直接合并基于 v18 的 PR #83，以免回退后续 Protocol Lab、Provider Set、运行刷新和完整向导。

## 升级说明

1. 可从旧版覆盖安装；Provider、Router、V2 Profile、模型目录和历史数据不会因安装而重置。
2. 建议对第三方 Codex Provider 重新运行一次深度探测并保存；探测会发送真实模型请求，可能产生少量费用。
3. 运行中的旧 Codex 任务保留创建时的 Provider。若提示 app-server 仍使用旧配置，请从 Provider 工具栏进入“Codex 状态与修复”，阅读中断提示后刷新，并新建任务验证。
4. Codex 对外仍使用 Responses；Chat 只是 CCSM 面向第三方上游的内部兼容传输，不需要把 Codex Desktop 改成 Chat 客户端。
5. macOS 未配置 Apple 签名/公证密钥时仍提供未签名 DMG/ZIP；各平台正式资产和 updater 签名以本 tag 的 GitHub Actions 为准。
