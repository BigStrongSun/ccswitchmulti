# CCSwitchMulti v3.19.2-23

这是一次面向 Codex 真实使用场景的阶段性大版本，完整汇总 `v3.19.2-16` 至 `v3.19.2-23` 的模型能力、Provider 分流、MultiRouter/V2 Sub-Agent 同步、协议适配、完整设置向导、运行态修复、历史恢复和 Windows 安全升级工作。相对 `v3.19.2-15` 累计完成 177 个提交、修改 248 个文件、约 6.45 万行新增；此前只存在于中间候选或短版说明中的能力，现在统一进入一个可安装、可自动更新的正式版本。

## 本次大版本解决了什么

- 第三方模型不再只依赖一个静态的 `Responses` 或 `Chat` 开关。CCSwitchMulti 会按 Provider 和模型分别验证两种上游协议，并保存可追溯的双协议证据。
- 深度探测不再使用“能返回一段文字就算通过”的浅测试，而是覆盖基础响应、SSE 流式、推理语义、强制工具调用和工具结果续轮五个阶段。
- 自动探测、手工协议覆盖、Provider 保存、MultiRouter 批量配置与 Universal 入口统一到同一套 Protocol Lab / Provider Set 后端工作流。
- Codex 的运行配置、当前 app-server、分页历史和界面历史查询兼容层被拆成独立状态；修复一个问题不会再掩盖另一个问题。
- Windows 上的端口接管、Codex 刷新和 CCSwitchMulti 替换改为身份校验、备份、回滚和健康验证事务，避免误杀、假成功及升级后的异常退出误报。

## 0. Provider 分流、MultiRouter 与 V2 Sub-Agent 的架构重做

### Provider 是配置真源，不再复制两套模型事实

- 用户维护的普通 Provider 负责 endpoint、认证、协议、模型目录、上下文窗口、输入模态、推理档位、Ultra、缓存、显示名、启用状态和排序；这些事实不再重复写进 MultiRouter 路由文档。
- MultiRouter schema v2 只保存真正的路由策略：目标 Provider、`all/include` 模型选择、别名、认证策略、路由启用与顺序、Sub-Agent 候选和 V2 Profile 配置。运行时每次从最新 Provider 快照编译，不使用陈旧目录副本。
- 用户所理解的“Broker/Provider 分流”实际由 `Provider SSOT + MultiRouter 编译/投影` 完成，并不是新增一个需要单独维护的 BrokerProvider 类型；前端仍保持普通 Provider 和 MultiRouter 的扁平卡片结构。

### 跨模型分流与自动跟随

- `mode=all` 表示跟随目标 Provider 的全部启用模型：Provider 新增、删除、停用、改名、改协议、改上下文或推理能力后，Router、模型目录和已初始化 V2 Sub-Agent 会在同一变更链中重新编译。
- `mode=include` 表示用户明确维护的模型白名单：Provider 能力字段仍自动更新，但不会擅自把新模型加入用户的选择范围；已删除或不可路由条目保留诊断，不会静默改投其它来源。
- 多个 Provider 可贡献同名或不同名模型；公开名、上游名和路由别名分别保存，冲突时生成稳定可见名。请求日志和状态页解析到真实目标 Provider，而不是只显示内部 route ID。
- Provider 的增删改、模型排序和启停统一经过 Provider mutation 管线，Router、V2 Agent、目录缓存和 live 投影共享同一依赖指纹；不再由三个页面各自拼接并写回不同版本。

### MultiRouter 的同步边界

- 数据库中的 Router 是策略真源，运行文件是可丢弃投影。可同步内容仅包括聚合模型目录、`models_cache`、当前配置指针/指纹、受管 Agent TOML、投影状态与前端查询缓存；认证、Common Config 和用户自有 TOML 字段不会被 Router 回写。
- 只有当前活动 Router 可以发布共享 Codex 目录；活动归属不明确时 fail closed，避免两个 Router 依次覆盖同一个文件。停用 Router 可以更新数据库中的 V2 Profile，但不会覆盖当前 live 配置。
- 未勾选、已停用、未匹配或身份歧义的模型严格 fail closed，不再回退到默认 Provider 或第一条路由。Provider 删除、别名迁移与历史 current 修复也以逻辑 Provider 为边界。

### V2 Sub-Agent 与 Provider 同步

- V2 Sub-Agent 的模型来源来自 Router 编译后的 Provider 目录，不再使用独立的陈旧模型清单；角色名称、描述、开发者指令、昵称候选、推理策略和输入模态都区分自动值与手工覆盖。
- `mode=all` 的 Provider 新增模型后，会为已初始化的 V2 Agent 补建默认关闭 Profile；停用或删除模型时保留原 Profile 并标为不可路由，避免用户配置被静默删除。
- 模型别名、同名消歧和 Provider 目录变化会同步重定向 Profile 与 `spawnAgentModels`；写入、投影和回读校验使用同一 Provider 上下文，避免“文件写了但校验说不存在”。
- 工作台和设置向导都读取同一份 V2 诊断；空自动字段会显示模型不在投影目录、路由排除或别名不匹配等原因，不再只留一个无法解释的空表单。

## 1. 自动协议探测与 Provider Set

### 生产等价的双协议探测

- 每个启用模型分别测试 OpenAI Responses 与 Chat Completions；固定协议的官方/OAuth 来源不会被重复计费探测。
- 探测请求与真实代理请求共用请求准备逻辑，覆盖 endpoint、认证、公开模型到上游模型的映射、Custom User-Agent、Header/Body override、推理参数和请求预算。
- 探测证据按 Provider、模型、协议和完整请求指纹独立保存。endpoint、Key、模型映射、UA 或 override 变化后，旧证据会标为过期，不会被误用为当前结果。
- Responses 流必须到达合法终态；只有 `response.created` / `response.in_progress` 后提前结束的 HTTP 200 不再被误判为成功。
- HTTP 521、其它 5xx、网络、超时、401/403/429 和非法响应会保留真实的认证或可用性分类，不会被写成“模型不支持该协议”。错误展示经过脱敏，不包含 API Key、完整 endpoint、prompt 或上游响应正文。

### 自动选择、手工覆盖与原子保存

- 所有模型最终协议一致时，保存为一个严格单协议 Provider；同一逻辑 Provider 内模型协议混合时，保存为一个可见门面和内部同协议叶子。
- 内部叶子不会出现在普通 Provider 列表，也不能被直接编辑、切换或删除；用户仍看到原有扁平列表，只通过 `Responses`、`Chat` 或“自动适配 · Responses + Chat”小标记识别状态。
- 高级模式允许逐模型选择“跟随自动 / Responses / Chat”。手工覆盖不要求伪造探测成功；缺少对应证据时允许保存，但会显示风险提示。
- 自动 Single 与自动 Split 都直接由一次原子事务提交，不再出现没有实际选择价值的“是否拆分”二次确认。
- 旧 `modelCatalog[].apiFormat`、旧 Provider 级手工协议和旧混合 Provider 会在正常保存时迁入新的覆盖与证据模型，不增加额外迁移页面。
- Prepare/Commit 对 receipt 过期、重复消费、依赖变化、事务回滚、current Provider 和投影失败均有明确边界；投影失败会报告“已保存、待刷新”，不会把数据库已经成功提交误报成保存失败。

## 2. 推理、流式与工具调用语义

- 可读的上游 raw reasoning 始终映射为 `reasoning_text`；只有上游原生 summary 才映射为 `reasoning_summary_text`。代理不再为了让界面显示而把完整推理伪装成摘要，也不会自行编造摘要。
- Responses 工具续轮区分三种真实回放策略：原生 reasoning item、真实 `reasoning_text` content，以及只省略 reasoning 但保留工具调用与工具结果。只有明确的 400/422 replay-shape 拒绝才允许按序降级。
- 第三方 SSE 长时间无 token 时增加 keep-alive，减少代理、网关或负载均衡器把仍在推理的请求提前切断。
- 修复 Responses 提前 EOF、工具调用终态、强制工具阶段和工具结果续轮的判定边界，避免未完成任务被当成正常结束后直接甩出最终结果。
- 修复模型名称重映射后推理档位能力丢失，以及 Qwen/第三方模型错误继承 `reasoning_effort=none` 的问题；不受支持的档位按能力契约钳制到最近可用值，避免请求因 `high` 等档位返回 422。
- 模型排序保存改为原子更新，目录默认模型与用户排序不会再互相覆盖。

## 3. 完整 MultiRouter 配置向导

- 恢复并迁移完整的 13 页引导：开始、环境检查、来源就绪、来源选择、目录同步、协议深探测、模型选择、模型顺序、推理、Sub-Agent/工具、路由确认、保存启用和真实请求验收。
- 当用户一个 Provider 都没有时，动态插入第 14 页“接入第一个模型源”，并在新增完成后根据真实 Provider ID 自动选中，不再按名称、索引或临时草稿 ID 猜测。
- 后续页面可以预览，但在前置步骤完成前不可编辑，并明确提示需要先完成哪一步；侧栏导航只改变当前页面，不再篡改探测、保存或启用状态。
- 模型目录同步与协议深探测分成两个步骤。协议页明确展示 Responses/Chat、SSE、推理、强制工具和续轮，不再出现“基础探测、1024 输出、不验证工具/流式”的旧流程。
- 进度聚合按整次批量工作流统计，不再把最后一个 Provider 的完成事件当成全部结果；同名模型使用 `(Provider, model)` 作为身份并显示 Provider 标签，不会跨来源折叠。
- Qwen 等来源即使后端漏回单个进度事件，也会生成具名阻塞失败，不再出现“0/0/0 但可以继续”的矛盾终态。
- 保存成功后继续提供推理强度、Sub-Agent、模型顺序和历史修复的后续入口；批量保存仍使用当前原子 Provider Set 事务，而不是恢复旧向导的逐个写入。

## 4. Provider 编辑与统一 Protocol Lab 工作流

- 新增统一 Editor Snapshot 与批量适配摘要，一次读取逻辑 Provider、Single/Split 状态、逐模型实际协议、双协议证据、过期时间和投影状态；保存后重开页面能够恢复真实状态。
- Add/Edit、MultiRouter Wizard 和 Universal 入口共用同一状态机：读取、草稿失效、探测授权、实时进度、Prepare、Commit、阻塞、一次自动重探和投影警告拥有一致行为。
- 探测结果只更新工作流和后端读模型，不再由前端直接改写顶层 `apiFormat`；逐模型覆盖只写 Provider meta，不污染模型目录。
- 普通用户只看到测试、进度、结果、失败阶段和重试；高级用户可在原模型行内覆盖协议，不增加树状 Provider 页面或新的导航层级。
- 真正的 MultiRouter 继续标记为 `MultiRouter`；自动协议门面与它使用不同的小标记，保持现有 Provider 卡片结构和未来 Agent Mesh 扩展空间。

## 5. Codex 配置所有权与启动顺序

- 配置一致性只比较 CCSwitchMulti 拥有的模型、活动 Provider、目录指针和受管路由字段。
- Codex 合法维护的 `agents.*`、`desktop.*`、`developer_instructions`、MCP command/env、插件开关和 `projects.*.trust_level` 会被保留，不再触发“Codex 配置与 CCSM 不一致”。
- 所有托管写入基于最新磁盘快照合并，并使用 compare-and-swap 重试；不会通过恢复整份旧备份覆盖 Codex 新写入的非托管字段。
- “随 CCSwitchMulti 启动 Codex”现在位于启动门禁之后：先完成数据库与模型目录恢复、托管配置投影、15721 接管和复检，再允许启动 Codex。失败时阻止启动并记录明确阶段，避免 app-server 在旧配置上先启动并冻结旧 Provider。
- Codex 已经运行时保持幂等，不会因启动门禁被自动关闭；需要刷新时由独立、带确认的“Codex 状态与修复”流程处理。
- 托管激活使用独立指纹和实质变化时间，不再把整个 `config.toml` 的 mtime 当成配置生效时间。Codex 启动后写入 trust、桌面或插件字段不会造成“仍在使用旧配置”的误报。

## 6. Codex 状态刷新与历史恢复

- Provider 工具栏提供常驻“Codex 状态与修复”入口，先做非破坏性检查，再由用户确认关闭、重投影、重开和验证。
- 运行结果分为三项：配置与 app-server 生效、分页历史文件/投影状态、Renderer 跨 Provider 历史查询兼容层。界面兼容层失败只显示警告并允许单独重试，不再覆盖前两项已成功状态。
- Windows 新版 Codex 的 `ChatGPT.exe` 桌面壳与独立 `codex.exe app-server` 都进入身份快照；关闭窗口不再被误认为完整退出。
- 刷新只逐个结束预检且重新核验过路径、命令行、启动时间和身份的 PID，删除了可能递归误杀 CCSwitchMulti 的 `taskkill /T`。
- Renderer 兼容层适配新版动态 chunk、`appServices.localThreadCatalog`、React fiber 中的真实请求客户端以及新旧目录接口；跨 Provider 历史查询把 app-server 异常处理的 `modelProviders: null` 规范化为 `[]`，然后调用 Codex 自己的目录刷新，不改写任务的 Provider 元数据。
- 对超长单任务内因相邻重复 ordinal 导致的分页停滞，修复器只处理可证明安全的递增/相邻重复序列，保留每条 JSON 记录和同目录备份后原子替换；非重复回退或断档会 fail closed，不重置历史数据库，也不通过修改 mtime 伪造恢复。

## 7. Windows 端口接管与安全升级

- 15721 被旧 CCSwitchMulti 占用时提供“解除占用并恢复接管”。后端先核验 listener PID、路径、启动时间和文件身份，只接受当前 CCSwitchMulti 的已验证旧实例；未知程序、PID 复用或端口再次被抢占都会拒绝处理。
- 识别 Windows AppContainer 对安装目录的 LocalCache 投影时使用卷/文件 ID 证明同一文件，不再因字符串路径不同把自己的旧实例误判为外部程序。
- 本地安装替换事务包含：进程身份复核、停止、等待端口释放、精确退役旧运行 marker、配置静止快照、备份、安装、payload 哈希、单 listener、健康与 takeover 校验；任何关键步骤失败都会回滚或 fail closed。
- 计划内升级会按 PID、规范化路径、版本和进程启动时间退役自己拥有的运行 marker，不再把成功替换误报成 CCSwitchMulti 意外退出。
- 启动恢复、配置一致性、异常退出和路由接管提示按优先级串行展示，避免多个弹窗互相遮挡或留下无法点击的界面。

## 8. Provider 与模型兼容性修复

- Qwen/vLLM：能够识别 Responses 流只到 `created/in_progress` 的异常结束，并在 Chat 完整通过时保留 Chat 为安全协议；不会静默修改远端 vLLM。正式安装态已验证 Qwen Chat 的基础响应、SSE、推理、强制工具和续轮全部通过。
- GLM、Kimi、DeepSeek、MiniMax 等来源不再靠名称硬编码结论，而是按当前 endpoint、模型和实际协议结果保存。网络失败和上游 5xx 会保持可用性错误，恢复后可重新探测。
- MultiRouter V2 认证 schema 统一使用 `source` / `accountId`，修复旧 `authProvider` 字段导致的保存失败，并保持 OAuth 身份和 Provider Set 提交原子性。
- 自动拆分的内部叶子不会泄漏到普通列表或成为可直接操作对象；历史 current、路由迁移、删除和切换均以逻辑 Provider 为边界。
- Provider 探测与真实运行使用相同的 User-Agent、Header/Body override、认证和模型映射，避免“探测通过、Codex 实际请求失败”或反向误判。

## 9. Guardian V2 / FeatureToml 根因修复

- Renderer V6 将模型白名单修改严格限制到对应 Statsig 配置，不再把 `available_models`、`default_model`、`use_hidden_models` 注入 Guardian V2 或其它动态配置。
- 启动时可清理由旧 V5 兼容层造成的三个污染字段，同时保留 Guardian 的 `enabled` 和其它未知字段。
- 只有 app-server 明确返回 `FeatureToml in features.guardianv2` 时，才把当前请求的 Guardian 对象按 `enabled` 降级为布尔值并重试一次；网络错误、其它 feature 和原始请求不会被泛化重试。
- 该问题的报错虽然声称无法加载 `config.toml`，实际故障位于 Renderer 请求级功能覆盖；本版本从真正的污染源修复，不再依赖反复重写磁盘 TOML。

## 升级与使用说明

1. 可直接从旧版覆盖安装；Provider、路由、模型目录和历史数据不会因安装而重置。
2. 升级后建议在每个第三方 Codex Provider 的“模型与兼容性”中重新运行一次深度探测并保存。探测会发出真实模型请求，可能产生少量费用。
3. 运行中的旧 Codex 任务会保留创建时的 Provider。若状态页提示 app-server 仍使用旧配置，请使用“Codex 状态与修复”，阅读中断提示后再刷新，并在重开后创建新任务验证。
4. `Partial` 或 `Failed` 不一定代表 CCSwitchMulti 故障。请先查看失败阶段；HTTP 5xx、网络和认证错误表示当前上游不可用，恢复后可重新探测。
5. Codex 对外仍使用 Responses；Chat 是 CCSwitchMulti 在第三方上游内部采用的兼容传输，不需要把 Codex Desktop 改成 Chat 客户端。
6. macOS 在仓库没有 Apple 签名和公证密钥时仍发布未签名 DMG/ZIP；Windows、Linux 和 macOS updater 资产及签名由 tag 对应的 GitHub Actions 生成。
