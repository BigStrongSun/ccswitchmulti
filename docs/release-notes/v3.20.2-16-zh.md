# CCSwitchMulti v3.20.2-16

修掉一次网络抖动就会导致 OpenAI Official 线路长时间彻底不可用的缺陷。

## 问题

2026-09-15 09:17:59 起，访问 chatgpt.com 的 TLS 握手连续失败（`unexpected EOF during handshake`）。随后约半小时内，每次 Codex 请求都在 **3 毫秒内** 返回 `503 无可用 Provider`，日志里没有任何上游请求记录——请求根本没有发出去。

根因是 OAuth 账号池的软避让被当成硬失败：

- 网络层的瞬时失败被计为**每个账号各自**的连续失败。两个账号分别在 09:18:35 前连续 9 次、09:19:12 前连续 6 次失败，按升级梯度（30s → 120s → 600s → **1800s**）各自进入 **30 分钟软避让**。
- 池内账号全部被软避让后，`ordered_pool_entries` 返回空 → 账号池展开后没有任何候选 → 路由直接返回 `503 无可用 Provider`，**从不访问上游**。
- 因为从不尝试，就永远拿不到成功记录来清除软避让，网络恢复后仍要等满 30 分钟才能自愈。错误文案也没有说明这是账号池状态。

## 修复

- **软避让只作为偏好**：池内账号全部处于软避让/额度冷却时，按“最早恢复”的顺序回退放行，让请求真正打到上游并返回真实结果（成功或上游错误）。凭据失效、需要重新登录、额度低于保留值仍然不参与，保持 fail-closed。
- **补齐诊断日志**：账号池回退时会记录最早恢复时间与候选数；账号池没有任何候选时记录 `[CodexOAuthPool] [POOL-001]`，不再出现“日志里什么都没有的 503”。
- **错误文案说清原因**：`503` 的 cause 从 `无可用 Provider` 改为 `无可用 Provider（没有可尝试的上游候选：账号池全部不可用或全部被熔断拒绝）`。

## 验证

- 新增回归用例 `all_soft_avoided_accounts_still_probe_earliest_recovery`：三个账号（含 native）各累计 3 次瞬时失败进入软避让后，仍必须返回全部候选（旧实现返回空）。
- `cargo test --lib proxy::` 1968 passed / 0 failed；`cargo fmt` 通过。
- 现场证据：`proxy_request_logs` 中官方线路自 09:19:13 起 240 次请求 100% 为 3–6ms 的 503；`codex-router.log` 中最后一次真正访问上游是 09:19:12，与两个账号各自触发 30 分钟软避让的时刻完全吻合。
