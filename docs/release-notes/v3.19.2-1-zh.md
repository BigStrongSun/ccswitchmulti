# CCSwitchMulti v3.19.2-1

本版本重点修复 Codex 长任务被 `429 Too Many Requests` 直接打断的问题：当上游明确拒绝本次请求且尚未开始生成时，CCSwitchMulti 会在本地代理内等待并自动续传同一请求，尽量让当前 Codex turn 无感恢复，而不是立即结束线程中的当前工作。

## 重点修复：Codex 429 自动续传

### 问题根因

现行 Codex Rust 客户端对模型 Provider 固定使用 `retry_429 = false`。因此，Responses 接口在建立成功流之前直接返回 HTTP 429 时，客户端可能一次都没有重试，却仍显示：

```text
exceeded retry limit, last status: 429 Too Many Requests
```

这会终止当前 turn。线程和历史通常仍然存在，用户点击“继续”后可以接着工作，但正在执行的长任务、远程操作或多 Agent 协作已经被打断。

### CCSwitchMulti 如何恢复

- 仅当 CCSwitchMulti 已经收到上游明确的 HTTP 429 时，才判定本次请求被拒绝、尚未进入成功响应，并重发完全相同的请求头和请求体。
- 最多自动续传 5 次，与 Codex 默认的流恢复预算保持一致。
- 优先遵循上游 `Retry-After`；单次等待最长 60 秒，累计等待预算最长 180 秒。
- 上游没有提供 `Retry-After` 时，按 1 / 2 / 4 / 8 / 16 秒指数退避，避免立即连续冲击服务端。
- 续传发生在 CCSwitchMulti 代理内部，Codex 不会先收到 429，因此当前 turn 可以在上游恢复后继续取得正常响应。

### 防止错误重发

429 并不都代表同一种故障，本版本保留了严格的幂等边界：

- `usage_limit_reached`、`insufficient_quota`、`billing_hard_limit_reached` 等确定性额度耗尽不会在同一账号上空转；它们会立即交给现有 Codex 账号池或 MultiRouter 尝试其它可用候选，没有候选时原样返回客户端。
- CCSwitchMulti 自己的 `ResponsePending/429` 表示请求可能已经到达上游、结果仍未知，继续明确禁止重放，避免重复采样、重复工具调用和重复计费。
- 连接建立失败继续走既有传输重试；成功建立 SSE 后的中途断流继续走既有语义输出边界和 Codex 流恢复，互不混用。
- 所有重试均有次数和总等待预算，不会形成无限 429 循环。

## 验证

- 瞬时 `rate_limit_exceeded` 后，同一请求自动续传并恢复为 HTTP 200。
- 精确验证 `Retry-After` 秒数得到遵循。
- 精确验证 `usage_limit_reached` 不会在同一账号重复发送。
- 原有传输恢复测试继续通过：连接失败可恢复、`ResponsePending` 不重放、重试预算耗尽后停止。
- Windows x86_64 release 构建通过；GitHub Actions 将为 Windows、macOS 与 Linux 自动生成正式发布资产。

## 社区与源码依据

- OpenAI Codex issue [#30471](https://github.com/openai/codex/issues/30471) 记录了直接 HTTP 429 被显示为“exceeded retry limit”、且 provider 固定不重试 429 的现行行为。
- 旧版 TypeScript Codex PR [#506](https://github.com/openai/codex/pull/506) 曾实现最小 429 重试循环，但现行 Rust 客户端没有等价的可配置恢复路径。

本修复不声称所有 429 都来自 OpenAI 服务拥塞；429 也可能来自并发限制、速率限制、账户额度、网关策略或 CCSwitchMulti 的安全保护。CCSwitchMulti 现在根据请求阶段和错误语义分别处理，只自动续传能够确认尚未执行的真实上游 429。
