# CCSwitchMulti v3.19.1-26 分支汇总与历史功能收敛设计

## 背景

`v3.19.1-25` 是针对 Codex Windows Setup 阻断的紧急热修。它完整继承 `v3.19.1-24`，但没有吸收同日平行分支 `bigstrongsun/fix-portable-third-party-reasoning` 上已经完成的 Provider 与 MultiRouter 配置体验改进。该平行分支从较早历史分叉，整树合并会删除或回退 Sub-Agent V2、事务安装器、更新器和后续 release 主线，因此只能做选择性功能移植。

## 目标

- 以 `v3.19.1-25^{}` 的 `4d19b80a0c0f077de3968d3f12271924c6825a97` 为唯一、不可变基线。
- 把同日平行完成且尚未 patch-equivalent 的 Provider/MultiRouter 生产改动与回归测试纳入 `3.19.1-26`。
- 审计全部本地分支与 `fork/*` 远端分支，找出仍未进入 release 主线的历史功能分叉。
- 保留每项结论的 ancestry、patch-id、文件树、测试和产品边界证据，避免以后再次靠分支名猜测。

## 汇总方法

### 1. 不移动既有标签

`v3.19.1-25` 已推送并触发跨平台构建。`3.19.1-26` 使用新分支、新版本提交和新 annotated tag；不重写、删除或复用 `v3.19.1-25`。

### 2. 四级证据判定

每个候选分支依次检查：

1. `git merge-base --is-ancestor`：判断提交历史是否已进入基线。
2. `git cherry` / stable patch-id：识别不同 SHA 的等价移植。
3. 文件和数据合同对比：识别已被后续实现重构或替代、但 patch-id 不相等的功能。
4. 聚焦测试与完整回归：只有在当前 `v25` 主线真实通过的功能才允许进入 `v26`。

“不是祖先”不直接等于“功能缺失”；“patch-id 不同”也不直接等于“应该移植”。

### 3. 选择性移植范围

纳入以下同日功能组：

- Provider 路由入口收口和 `/model` 目录投影控制边界。
- 常显的模型同步、默认模型、协议探测、连接验证和可路由状态。
- Provider 专家配置与设置页 Codex 全局配置职责拆分。
- MultiRouter 从十个技术步骤收敛为四个用户任务。
- MultiRouter 成功后留在状态工作台，不再自动跳转历史修复。
- 上述功能的 RED/GREEN 测试和必要设计、审计说明。

Windows Setup 空 reasoning 数组修复已经以等价 patch 进入 `v25`，不得重复移植。

### 4. 必须保持的 v25 主线合同

- Sub-Agent V1/V2 两套设置、V2 capability profiles、问卷编辑器、独立 Sub-Agent 工作区和 managed role 投影完整保留。
- `settingsConfig.codexRouting`、历史 Provider route editor 数据、后端 resolver 和迁移兼容层继续存在；只收口可见入口。
- 事务式安装脚本、配置/注册表备份、回滚和健康检查不得删除或降级。
- 更新器、`latest.json`、发布工作流、历史修复独立入口和真实转发验证保持现有语义。
- 当前用户工作区中的未跟踪对比文件和其它 worktree 脏改不进入汇总。

## 历史分叉审计分类

所有未合并 refs 最终归入以下一种状态：

- `included-by-ancestry`：提交历史已在 `v26`。
- `included-by-patch`：不同 SHA，但 stable patch-id 等价。
- `superseded-by-current-tree`：旧实现已被当前主线更完整的实现取代。
- `docs-or-research-only`：仅报告、课件、论文或验收记录，不影响运行功能。
- `intentional-experiment/no-go`：实验结论明确不应产品化。
- `upstream-or-pr-scope`：上游同步、PR 评审或独立产品线，不属于本 release。
- `actionable-missing`：经过功能和测试审计后确认仍缺失；必须在 `v26` 集成，或记录明确 defer 决策、负责人和目标版本/跟踪项。未解决的 `actionable-missing` 会阻断 Task 10 和正式发布。

审计必须遍历全部 `refs/heads/*` 与 `refs/remotes/fork/*`，不以更新时间或 v3.19 分支起点过滤；每个相关 ref（包括非 release ref）都要列出 ref、tip、merge-base、唯一 patch 数、分类、依据和排除/不纳入 release 的明确理由。结果写入 `docs/audits/2026-08-14-v3.19.1-26-branch-divergence.md`。

## 提交与测试策略

- 设计/计划、RED 测试、GREEN 实现、分叉审计、memory、版本提交分别提交。
- 原提交已经具备 RED/GREEN 边界时按原顺序移植；冲突解决不得把 RED 测试改成无效断言。
- 每个提交正文最后一段必须为 `本次提交由BigStrongsSun完成`。
- 所有中间提交使用临时空 `core.hooksPath`，避免 post-commit release pipeline 并发构建；最终版本候选只手动运行一次发布流水线。

## 验收

- Provider 页面只承担单模型源配置，MultiRouter 工作台承担组合路由，Sub-Agent 保持独立工作区。
- 新建维护预设自动投影模型目录；自定义 Provider 保留高级退出能力。
- 四步向导和原地成功状态通过真实组件测试，历史配置数据不丢失。
- Rust 全库、前端全集、Pester、typecheck、格式、构建全部通过。
- 本地 `3.19.1-26` 安装器、portable、raw EXE、签名、版本资源和 SHA-256 一致。
- 事务安装后 CCSM `/health`、Codex `config/read`、Windows sandbox readiness 和实际路由正常。
- 远端 annotated tag、全部平台 jobs、Release、19 个资产、`latest.json` 和代表性下载哈希完成核验。
