# CCSwitchMulti v3.20.1-1 上游迁移设计

## 目标

以 CCSwitchMulti `main@3670daab32bd95edf6fa42478c33d031239fe253` 为产品基线，逐项吸收官方 `farion1231/cc-switch` 的 `v3.20.1@3217f725` 及迁移审计时 `origin/main@741e802f` 中适合 CCSwitchMulti 的改动，形成派生版本 `3.20.1-1`。

本迁移不是把官方分支机械合并到 CCSwitchMulti。目标是保留 CCSwitchMulti 已发布的 MultiRouter、Provider Set、Protocol Lab、动态官方模型元数据、账户池、历史修复和跨供应商协议证据边界，同时取得官方 3.20.0/3.20.1 的可靠性修复与新增能力。

## 已验证基线

- 官方最新正式版本为 `v3.20.1`，发布于 2026-08-28。
- 官方 `main` 在审计时为 `741e802f`，比 `v3.20.1` 多 31 个非合并提交；相对上一轮审计只新增 `741e802f`：GLM-5.3 内置价格。
- CCSwitchMulti `main` 与官方 `main` 的 merge-base 为 `43eaf073`，两侧独有提交数为 1611/131。
- `git merge-tree --write-tree main origin/main` 产生 83 个内容冲突，集中在数据库、Codex OAuth、代理转换、Provider 服务、设置、前端表单和版本源。
- 本地分支审计没有发现新的“已完成但未进入 main”的产品分支。Power、AgentMesh、reasoning probe、MultiRouter SSOT 和 error journal 现场继续按各自 NO-GO 或未完成边界保留。

## 决策

采用“分层语义迁移”，不采用整枝 merge 或以官方主线重基替换 CCSwitchMulti。

每项官方改动先回答四个问题：

1. CCSwitchMulti 是否已经有等价或更强实现？
2. 官方实现是否依赖官方数据库版本、Provider 结构或单账号假设？
3. 迁移后是否破坏 CCSwitchMulti 的 fail-closed、证据来源和用户显式选择边界？
4. 能否先用回归测试证明当前缺口，再实现最小的根因修复？

已被 CCSwitchMulti 覆盖的提交只记录映射关系，不重复移植。存在架构冲突的改动按意图重写并保留官方提交/PR 来源，不以冲突块的 ours/theirs 选择替代设计。

## 迁移批次

### 批次 0：审计清单和低风险数据

- 固定官方 tag、审计 tip、commit/PR、文件和行为矩阵。
- 迁移 GLM-5.3 价格种子；价格为 input 1.4、cached input 0.26、output 4.4 USD/MTok。
- 评估纯目录字段、模型能力标志和价格修正；任何能力字段仍须遵循 CCSwitchMulti 的动态官方元数据优先级。
- 不在该批次提升数据库 schema，不混入 Provider/OAuth 行为。

### 批次 1：基础可靠性

- 逐项评估 WSL 配置写入、Windows 版本检测、启动闪屏、备份原子性、导入完整性、同步串行化、无障碍标签和输入法修复。
- 对 CCSwitchMulti 已有备份、安装事务和 live-config ownership 先做行为对照；只迁移确实缺失的语义。
- UI 视觉整理不得覆盖当前 Provider 工作台、首次配置向导或 Protocol Lab 信息架构。

### 批次 2：数据库迁移映射

- 官方 v16→v17 和 v17→v18 迁移不能直接复用版本号；先映射到 CCSwitchMulti 当前 schema 的新单调版本。
- 新迁移必须支持 fresh database、逐版本升级、重复启动幂等、备份导入和失败回滚。
- Pi usage dedup、Codex history cursor 和 managed account identity 分开迁移、分开测试。
- 不在读路径增加掩盖损坏数据的临时容错。

### 批次 3：Codex OAuth 与账号身份

- 官方多 ChatGPT 账号、逐 Provider 绑定、重复账号拒绝和 managed-auth fallback 修复，必须与 CCSwitchMulti 的账户池、Provider health、认证所有权和官方动态模型目录统一。
- 禁止把官方“单绑定账号、不自动 failover”的假设覆盖 CCSwitchMulti 已发布的显式账户池策略。
- `auth.json`、数据库令牌包、请求身份、用量归属和切换后的 CLI 身份必须一致；不允许静默串账。
- 先建立账号重复、切换竞态、刷新令牌回采、退出登录和错误归属的 RED 回归。

### 批次 4：Codex/代理协议

- 分别迁移或判定已覆盖：Claude WebSearch→Responses、Codex Alpha Search、mid-conversation system message、Moonshot/Kimi `$ref`、DeepSeek search capability、parallel tool calls、xAI/Grok native Responses、whole-float integer 边界。
- 每个供应商行为都以 transport-neutral regression 证明，不按 hostname/model 名写特例来绕过协议证据。
- 保留 CCSwitchMulti 的 Chat/Responses 探测、Partial/Unverified 手动选择、工具续轮和历史 replay 约束。
- 官方 session rollout 修复与 CCSwitchMulti 的 lineage/pagination repair 先做数据模型对照，禁止直接叠加两套游标逻辑。

### 批次 5：Pi 与新增应用面

- Pi 作为独立受管应用接入，不挤入 Codex MultiRouter 或 Provider Set schema。
- 明确 models、prompts、skills、session usage、default provider/model 和 auth 的所有权；Pi 原生登录及默认选择保持由 Pi 自己管理。
- Provider 导入和 live 文件写入必须有版本检查、冲突拒绝、备份和幂等回归。

### 批次 6：前端与预设

- 迁移模型搜索、结构化 headers/options、账号选择、状态徽标和必要的表单一致性改进。
- 官方预设逐个验证 endpoint、认证、API dialect、reasoning 档位、工具与图像能力；不因官方仓库存在就自动标记为 CCSwitchMulti Verified。
- CCSwitchMulti 的高级覆盖、证据摘要、Provider Set 和 MultiRouter 编辑入口必须保持可达且不被旧官方表单覆盖。

### 批次 7：版本和发布

- 所有功能批次通过后，将 package、Tauri、Cargo 和 lockfile 版本统一为 `3.20.1-1`。
- 发布说明区分：官方继承、CCSwitchMulti 保留/重写、未采用的官方改动、数据库升级与降级要求。
- 版本提交不夹带未验证功能，不移动或复用既有 tag。

## Git 与工作区策略

- 实现使用隔离分支 `bigstrongsun/upstream-v3.20.1-migration` 和独立 worktree。
- 不清理、不重置、不合并现有未完成 worktree；主工作区 `.tmp/` 与 `docs/provider-settings-layout-preview.html` 保持用户所有。
- 每个迁移批次至少一个独立本地提交，提交正文记录官方来源、根因、冲突决策和测试证据，最后一段固定为 `本次提交由BigStrongsSun完成`。
- 不使用整枝 merge；必要的 cherry-pick 只用于依赖独立且与当前架构一致的原子提交，否则按行为语义重新实现。

## 验证门禁

每个批次：

- 先写能在当前 CCSwitchMulti 上失败的聚焦回归，再实现并复跑。
- 运行相关前端/Rust 测试、typecheck、rustfmt、严格 Clippy、`git diff --check` 和 UTF-8 无 BOM/U+FFFD 检查。
- 数据库批次额外覆盖 fresh、逐版本升级、幂等、备份导入和回滚。
- 协议批次额外覆盖非流式、SSE、工具调用、工具续轮、reasoning 和错误终止事件。

最终候选：

1. 在本机 Ryzen 9 9950X 上串行完成完整前端测试、Rust library 与 integration tests、`cargo check --all-targets`、严格 Clippy、renderer production build、sidecar、Tauri release 和 Windows NSIS 导出。
2. 从精确候选提交复算安装器、portable、raw executable 和 updater 元数据摘要。
3. 再运行 GitHub Windows、Ubuntu、macOS CI；跨平台条件编译全绿后才创建 `v3.20.1-1` tag。
4. Release workflow 的所有平台产物、签名和 `latest.json` 完成远端验收后，才声明正式发布完成。

## 停止条件

- 官方行为与 CCSwitchMulti 已发布不变量冲突且缺少足够证据时，停止该功能批次并记录 deferred，不用兼容开关掩盖。
- 发现数据库不可逆损失、身份串账、历史 lineage 合并、协议工具续轮退化或平台条件编译失败时，不进入下一批。
- 本地源码/测试通过不等于安装态通过；Windows 安装验收不等于三平台 Release 通过。

## 完成标准

- 官方 131 个独有提交全部在迁移矩阵中被分类为 adopted、already-covered、rewritten、deferred 或 not-applicable，并有理由和验证证据。
- 所有 adopted/rewritten 行为进入 `main`，不存在未解释的高风险冲突块。
- `3.20.1-1` 的本地构建、安装候选、三平台 CI、Release 资产和 updater metadata 均与同一 peeled commit 绑定。
- 未完成/NO-GO 分支和用户现场保持原样。
